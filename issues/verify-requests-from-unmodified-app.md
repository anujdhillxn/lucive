# Verify Requests Come from Unmodified App

## Problem

The server currently trusts any request that carries a valid auth token. There is no mechanism to verify that the request originates from an unmodified, legitimate build of the Lucive app. A motivated user could:

- Intercept API calls (via a proxy) and fabricate score uploads with inflated values.
- Modify the APK to disable rule enforcement while still reporting compliant scores.
- Replay or forge heartbeat/score payloads directly against the API.

This undermines the accountability model — the entire value proposition depends on scores being trustworthy.

## Possible Solutions

### 1. Android SafetyNet / Play Integrity API

Google's **Play Integrity API** (the successor to SafetyNet) provides a signed attestation that:
- The device passes integrity checks (not rooted/emulated in a suspicious way).
- The app binary matches the one distributed via Google Play (unmodified).
- The request was generated by a genuine app instance.

**Flow:**
1. Server generates a nonce and sends it to the client.
2. Client calls the Play Integrity API with the nonce, receives a signed JWT.
3. Client sends the JWT alongside the API request.
4. Server verifies the JWT with Google's servers and checks the `appRecognitionVerdict` field.

**Considerations:**
- Requires a Google Play Console account and server-side verification calls to Google.
- The API has rate limits on the standard (free) tier; classic requests are more expensive.
- Does not prevent all attacks (a user on a compromised device can still intercept at a lower level), but raises the bar significantly.
- Only works for Play-distributed builds; debug/staging builds will fail attestation unless excluded explicitly.

---

### 2. Certificate Pinning

Pin the server's TLS certificate in the Android network config so that proxying tools (Charles, mitmproxy) cannot intercept traffic even if the user installs a custom CA.

**Where to add it:** `res/xml/network_security_config.xml` with a `<pin-set>` for the server's certificate fingerprint, referenced from `AndroidManifest.xml`.

**Considerations:**
- Stops casual interception but not sophisticated attackers who can patch the APK to remove the pin.
- Must be updated whenever the server certificate is rotated.
- A useful baseline layer, but not sufficient on its own.

---

### 3. Request Signing (HMAC)

Embed a secret in the app (obfuscated via NDK/native code) and use it to sign each request payload with HMAC-SHA256. The server verifies the signature before processing the request.

**Considerations:**
- Secrets embedded in APKs can be extracted via reverse engineering, even with obfuscation. This raises the effort bar but is not cryptographically sound against a determined attacker.
- More useful as a second layer on top of Play Integrity than as a standalone solution.

---

### 4. Server-Side Anomaly Detection

Rather than preventing fabrication entirely, detect implausible score patterns:
- Scores that are suspiciously perfect (100% compliance every day).
- Score uploads that arrive without corresponding heartbeat data patterns.
- Heartbeat timestamps that are non-monotonic or suspiciously regular.

Flag anomalous accounts for review rather than trying to prevent all attacks at the network layer.

**Considerations:** Lower engineering effort, no dependency on Google APIs, and scales naturally. The trade-off is that it is reactive rather than preventive.

---

## Recommended Approach

For the current stage of the product, **certificate pinning + server-side anomaly detection** is the pragmatic starting point — low effort and covers the most common attack vectors. **Play Integrity API** should be added once the app has meaningful scale, as it is the only solution that verifiably attests the binary.
